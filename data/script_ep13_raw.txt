You download a local AI model that promises a context window of one hundred and twenty-eight thousand tokens. That sounds enormous. Enough for a long report, a mountain of code, or an entire conversation that never seems to end.

Then you load the model. You paste in a document. Your GPU memory fills up, the first answer takes forever, or the application refuses the request. And if it does answer, it confidently misses a detail you know is sitting right there in the text.

What happened to those one hundred and twenty-eight thousand tokens?

Here is the trap: a model can advertise a large context window without your computer being able to run that window efficiently. And even when the text fits, that does not guarantee the model will use every part of it correctly.

Today we are following one long prompt through a local AI system, from the model specification to the GPU memory, all the way to the answer. We will find out what actually runs out, why long conversations slow down, and when a smaller, smarter context can beat a gigantic one.

First, forget the idea that context is permanent memory. A context window is the working information made available to the model for a particular generation. It can contain instructions, prior messages, documents, tool results, and the beginning of the model's own response.

A token is not necessarily one word. Depending on the tokenizer, a word can be one token, several tokens, or part of a token sequence. Punctuation, code, special chat markers, and formatting also count. So a one-hundred-page document cannot be converted into a reliable token count using page numbers alone.

And the full context budget is not always yours to spend on the input. In many runtimes, prompt tokens and generated tokens share the configured context limit. If you fill the entire allowance with source material, you may leave no room for the answer. Separate model or application output limits may apply as well.

So imagine a hypothetical one-hundred-and-twenty-eight-thousand-token budget. If you want the model to generate eight thousand tokens, you need to leave enough space for those eight thousand plus any system prompts, chat formatting, and other overhead. One hundred and twenty-eight thousand tokens is a ceiling, not a promise that you can paste in that much text and still receive a full response.

Now comes the first of four separate limits. The model itself has a supported context configuration. That number may come from its architecture, training setup, and published configuration. Some models are designed or adapted for longer sequences than others.

The second limit belongs to the software running the model. A local application may choose a smaller active context than the model's published maximum. Changing the model file does not force the application to use the largest supported value.

For example, llama.cpp exposes a context-size setting. vLLM exposes a maximum model length setting. Both also have other configuration and memory constraints. The exact command names and behavior depend on which version and backend you are running. The important point is that the advertised model limit and the configured runtime limit are different facts.

The third limit is physical memory. Not just the model weights. Not just the file you downloaded. The memory needed while the model reads and generates.

This is where the key-value cache enters the story.

When a transformer processes earlier tokens, its attention layers calculate representations called keys and values. During autoregressive generation, a supported caching implementation saves those representations so the model does not need to recompute the entire past in exactly the same way for every new token.

Think of it as a growing set of working notes for the current request. The model weights are the machinery. The key-value cache is some of the temporary state the machinery needs to keep track of the conversation.

For an ordinary full-attention transformer with a conventional cache, longer sequences need more stored key and value data. Cache memory scales with token count, with the number of layers, with the key-value heads and their dimensions, with the storage precision, and with how many sequences are being served.

Here is a calculation, but listen carefully: this is a made-up architecture for explaining the math. It is not a measured benchmark for any GPU or named AI model.

Imagine thirty-two layers, eight key-value heads per layer, one hundred and twenty-eight values per head, and two bytes for each stored value. Every cached token needs both a key and a value. With that hypothetical design, a thirty-two-thousand-token cache occupies about four gibibytes before implementation overhead and any other allocations.

At eight thousand tokens, the same illustrative cache would occupy about one gibibyte. At one hundred and twenty-eight thousand tokens, it would be about sixteen gibibytes.

That is the shock. The model weights could already fit comfortably on a graphics card, while the context cache pushes the whole workload over the edge. Reducing the weight file through quantization does not automatically reduce the cache to the same precision.

The specific cache numbers change with the actual model architecture. Grouped-query attention can reduce the number of key-value heads. Sliding-window and other attention patterns can change which tokens a layer needs to retain. Some runtimes use quantized or offloaded caches. So never copy those four-gibibyte numbers onto an unrelated model and call them specifications.

But the principle is real: fitting the weights is not the same as fitting a long conversation.

Now think about what happens when the runtime is also serving more than one request. A chat server might hold active state for multiple users. Depending on its scheduling and cache design, the available memory must support those active sequences too. A context size that works for one short chat may not be practical with long requests running at the same time.

This is why you sometimes see errors about insufficient cache memory even after the weights have loaded. And it's why blindly raising the context setting can make a previously stable system stop launching.

The fourth limit is more subtle. Even if the model supports the tokens, the runtime accepts them, and the hardware stores them, the model may not use all that information reliably.

Long-context research has demonstrated that the position of a fact can influence whether a model retrieves it correctly. In the study called Lost in the Middle, the researchers found cases where information near the beginning or the end of a long input was easier for tested models to use than information buried in the middle.

That is not a claim that every modern model always forgets the middle. Results differ by model, task, and evaluation. It is a warning that a large numerical context limit is not the same as reliable recall across the entire window.

Imagine giving a model forty reports. One report, buried halfway through, contains the single number that answers your question. You may discover that changing the order of those reports changes the answer, even though none of the facts changed.

This is why one of the most useful long-context tests is not asking whether the model loads a giant document. It is placing the same important detail near the beginning, the middle, and the end, and checking whether the answers stay correct.

Now let's follow the clock, not just the memory meter.

Before a model can produce the first answer token, it must process the input prompt. That initial pass is often called prefill or prompt processing. A very long prompt can demand substantial computation and data movement, even when the final answer will only be a few sentences.

Then comes decoding: generating output tokens, usually one step after another. The cache helps by reusing prior key and value states, but it does not make a very long context free. Attention and memory traffic still matter, and implementations vary.

That gives you two separate speeds to measure. How long did it take to get the first token? And how quickly did the answer arrive after generation started? A system can generate tokens quickly once it begins, yet feel painfully slow because it spent so long reading the prompt.

There are clever optimizations. Flash Attention and related kernels reduce certain memory and computation costs. Cache quantization can save space on supported backends. Prefix caching can reuse work when requests share an identical prefix. Some engines can move cache data to other memory. But none of these features automatically turns the largest advertised context into the best setting for every task.

And there is another trap: making the context longer through positional-scaling settings is not the same as proving that the model remains accurate at the new length. A runtime may let you change positional parameters. That does not guarantee the model was trained or validated to reason reliably across that expanded window.

So what should you do instead of immediately setting everything to one hundred and twenty-eight thousand?

First, find the real context limit published for the exact model version, and check the running application's configured limit. Record both numbers. Do not assume the model page and the software settings agree.

Second, inspect the runtime logs. Check where model weights are loaded, how much cache memory is allocated, which cache precision is active, and whether any memory has been placed on the CPU. If your interface hides those details, use the backend logs or supported diagnostics.

Third, test the workload you actually care about. Start with a modest context. Then increase it in steps using the same model, the same quantization, and the same questions. Record available VRAM, the prompt-processing time, time to first token, and output generation speed.

Fourth, test answer quality. Put one known fact near the start, one in the middle, and one at the end of a document. Ask precise questions with answers you can independently verify. Repeat with more than one example. A successful model load is not a successful comprehension test.

Fifth, reserve space for the answer. Count the system instructions, previous messages, inserted documents, tool results, and expected output. If the application silently truncates older messages or shifts the context, learn exactly what it keeps and what it discards.

And sixth, question whether the model needs the whole document at once.

For searching a knowledge base, a retrieval system can locate a smaller collection of relevant passages and pass those passages to the model. That is the basic idea behind retrieval-augmented generation, or RAG. It is not a magic cure. Retrieval can select the wrong passages, omit a crucial detail, or lose context needed to interpret a quotation.

But when the task is answering a question from a large collection of documents, focused retrieval may be more useful than pouring every page into the prompt. For whole-book editing, complex cross-document reasoning, or questions that depend on broad structure, you may still need larger context, careful chunking, or multiple passes.

The correct strategy depends on the task, not on whichever context number looks biggest in a model comparison table.

And one final distinction matters. Saving a chat transcript on disk is not the same as keeping every line inside the model's active context. Your application might retrieve, summarize, or drop older material. That can be useful engineering. But if it isn't transparent, the model can seem to remember something one moment and forget it the next.

So here is the verdict. There is a model limit. There is a runtime limit. There is a hardware limit. And there is an effective-use limit. Those four numbers do not have to match.

A one-hundred-and-twenty-eight-thousand-token label can describe a supported capability. It does not promise that your current GPU has enough memory, that your interface is configured to use it, that the first answer will arrive quickly, or that every fact inside the window will be retrieved correctly.

Before buying more hardware or changing every advanced setting, measure the real bottleneck. Is the prompt being truncated? Is the cache running out of memory? Is prefill taking too long? Or is the answer simply wrong even though all the evidence fits?

Those problems require different solutions. And solving the wrong one can cost you hours, money, or the very accuracy you were trying to improve.
